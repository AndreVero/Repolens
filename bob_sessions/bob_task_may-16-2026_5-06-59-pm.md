 83 | # Testing
 84 | 
 85 | To facilitate testing of components, **Now in Android** uses dependency injection with
 86 | [Hilt](https://developer.android.com/training/dependency-injection/hilt-android).
 87 | 
 88 | Most data layer components are defined as interfaces.
 89 | Then, concrete implementations (with various dependencies) are bound to provide those interfaces to
 90 | other components in the app.
 91 | In tests, **Now in Android** notably does _not_ use any mocking libraries.
 92 | Instead, the production implementations can be replaced with test doubles using Hilt's testing APIs
 93 | (or via manual constructor injection for `ViewModel` tests).
 94 | 
 95 | These test doubles implement the same interface as the production implementations and generally
 96 | provide a simplified (but still realistic) implementation with additional testing hooks.
 97 | This results in less brittle tests that may exercise more production code, instead of just verifying
 98 | specific calls against mocks.
 99 | 
100 | Examples:
101 | - In instrumentation tests, a temporary folder is used to store the user's preferences, which is
102 |   wiped after each test.
103 |   This allows using the real `DataStore` and exercising all related code, instead of mocking the 
104 |   flow of data updates.
105 | 
106 | - There are `Test` implementations of each repository, which implement the normal, full repository
107 |   interface and also provide test-only hooks.
108 |   `ViewModel` tests use these `Test` repositories, and thus can use the test-only hooks to
109 |   manipulate the state of the `Test` repository and verify the resulting behavior, instead of
110 |   checking that specific repository methods were called.
111 | 
112 | To run the tests execute the following gradle tasks: 
113 | 
114 | - `testDemoDebug` run all local tests against the `demoDebug` variant. Screenshot tests will fail
115 | (see below for explanation). To avoid this, run `recordRoborazziDemoDebug` prior to running unit tests.
116 | - `connectedDemoDebugAndroidTest` run all instrumented tests against the `demoDebug` variant.

120 | tests against _all_ build variants which is both unnecessary and will result in failures as only the
121 | `demoDebug` variant is supported. No other variants have any tests (although this might change in future).

  1 | # Architecture Learning Journey
  2 | 
  3 | In this learning journey you will learn about the Now in Android app architecture: its layers, key classes and the interactions between them.
  4 | 
  5 | 
  6 | ## Goals and requirements
  7 | 
  8 | The goals for the app architecture are:
  9 | 
 10 | 
 11 | 
 12 | *   Follow the [official architecture guidance](https://developer.android.com/jetpack/guide) as closely as possible.
 13 | *   Easy for developers to understand, nothing too experimental.
 14 | *   Support multiple developers working on the same codebase.
 15 | *   Facilitate local and instrumented tests, both on the developer’s machine and using Continuous Integration (CI).
 16 | *   Minimize build times.
 17 | 
 18 | 
 19 | ## Architecture overview
 20 | 
 21 | The app architecture has three layers: a [data layer](https://developer.android.com/jetpack/guide/data-layer), a [domain layer](https://developer.android.com/jetpack/guide/domain-layer) and a [UI layer](https://developer.android.com/jetpack/guide/ui-layer).
 22 | 
 23 | 
 24 | <center>
 25 | <img src="images/architecture-1-overall.png" width="600px" alt="Diagram showing overall app architecture" />
 26 | </center>
 27 | 
 28 | > [!NOTE]  
 29 | > The official Android architecture is different from other architectures, such as "Clean Architecture". Concepts from other architectures may not apply here, or be applied in different ways. [More discussion here](https://github.com/android/nowinandroid/discussions/1273).
 30 | 
 31 | The architecture follows a reactive programming model with [unidirectional data flow](https://developer.android.com/jetpack/guide/ui-layer#udf). With the data layer at the bottom, the key concepts are:
 32 | 
 33 | 
 34 | 
 35 | *   Higher layers react to changes in lower layers.
 36 | *   Events flow down.
 37 | *   Data flows up.
 38 | 
 39 | The data flow is achieved using streams, implemented using [Kotlin Flows](https://developer.android.com/kotlin/flow).
 40 |

 74 |

 77 |
